# 持续补齐工程化

2026-10-22 对项目的工程化检查做了一次审计，结论是：格式（Prettier）与类型（tsc strict）已配置并进 CI，但有两个缺口。两个缺口均已在同日补齐，本文记录解决过程与注意事项。

## 审计发现的缺口

- **缺口一：没有 ESLint。** Prettier 只管格式，`any` 滥用、`no-console` 等代码质量规则无人管控。
- **缺口二：`tsc --noEmit` 只检查 `src/`。** 原 `tsconfig.json` 的 `include: ["src"]`，导致根目录的 `vite.config.ts`、`playwright.config.ts` 与 `tests/e2e/` 下的用例在本地和 CI 都无人做类型检查。

## 缺口二的解法：tsconfig 按文件类别拆分

标准做法（Vite 官方脚手架同款思路）：把单一 tsconfig 拆成解决方案根配置 + 按文件类别划分的子项目，再串一条 typecheck 命令。

```
tsconfig.json          ← 解决方案根配置：files: []，只放 references
├── tsconfig.app.json  ← src/（浏览器代码，types: vite/client、@webgpu/types，lib 含 DOM）
├── tsconfig.node.json ← vite.config.ts、playwright.config.ts（types: node）
└── tsconfig.e2e.json  ← tests/e2e/（types: node，lib 含 DOM）
```

### 操作步骤

1. `npm i -D @types/node`。此前项目没有这个依赖——`playwright.config.ts` 与 `webgpu.spec.ts` 都用了 `process.env.CI`，这正是一直没人检查它们的原因之一。
2. 原 `tsconfig.json` 内容原样搬入 `tsconfig.app.json`，`include` 仍是 `["src"]`。
3. 新建 `tsconfig.node.json`、`tsconfig.e2e.json`，沿用全部严格选项（`strict`、`noUnusedLocals/Parameters`、`verbatimModuleSyntax`、`erasableSyntaxOnly` 等），只按文件类别调整 `types`/`lib`/`include`。
4. `tsconfig.json` 改为 `files: []` + `references` 指向三个子项目。
5. `package.json` 新增 `typecheck` 脚本，`build` 改为复用它：

```json
"build": "npm run typecheck && vite build",
"typecheck": "tsc --noEmit -p tsconfig.app.json && tsc --noEmit -p tsconfig.node.json && tsc --noEmit -p tsconfig.e2e.json"
```

6. `AGENTS.md` 同步更新命令说明与配置文件列表。CI 无需改动，它跑的 `npm run build` 自动带上了扩展后的类型检查。

### 设计决策与注意事项

**为什么必须拆开？** 三类文件需要的全局类型不同，混在一个 tsconfig 里会互相污染：把 `@types/node` 塞进浏览器项目的 `types` 数组，`setTimeout` 等全局类型会变成 Node 版本；反过来，`vite/client`、DOM lib 也不该出现在 Node 配置文件里。

**references 本身不负责“选配置”。** 文件归属由每个子配置自己的 `include` glob 决定；references 只是声明子项目清单，让“从根配置出发找子项目”的消费方（编辑器、`tsc -b`）能找到它们。三个子项目的 include 互不重叠（`src` / 根目录两个配置文件 / `tests/e2e`），因此归属唯一。

**三类消费方，行为不同：**

- 编辑器（TS 语言服务）：打开文件后向上找最近的 `tsconfig.json`，发现是解决方案根，就顺着 references 加载全部子配置，用各自 `include` 匹配当前文件，套用匹配项目的编译选项。拆分前编辑器里打开 `vite.config.ts`、e2e 用例时是没有严格检查的（它们不属于任何 tsconfig 项目），拆分后编辑器与 CLI 行为一致。
- `tsc` 命令行：根配置 `files: []` 意味着裸跑 `tsc` 不检查任何文件，必须用 `-p tsconfig.xxx.json` 逐一显式指定，这正是 `typecheck` 脚本的写法。没用 `tsc -b`，因为构建模式要求子项目是 composite，与 `noEmit` 的组合很别扭。
- 运行时工具：`npm run dev`（Vite）、`npm test`（Vitest）、`npm run test:e2e`（Playwright）**完全不读 tsconfig 和 references**，只转译、不做类型检查，文件范围由各自的配置决定（Vite 从 `index.html` 入口、Vitest 的 `include`、Playwright 的 `testDir`）。因此 `npm run dev` 时类型错误不会阻断运行，开发期的类型反馈靠编辑器，提交前的强制检查靠 `typecheck`。

### 验证结果

- `npm run typecheck`：三个项目逐一检查，零错误（含首次被检查的 `vite.config.ts`、`playwright.config.ts`、两个 e2e 用例）
- `npm run format:check`：新文件符合 Prettier 格式（tsconfig 里的注释 Prettier 按 jsonc 解析，没问题）
- `npm run build`：类型检查 + 生产构建通过
- `npm test`：10 个单元测试全部通过
- e2e 未在本地重跑，改动不影响其运行时行为，CI 会覆盖

## 缺口一的解法：引入 ESLint

完整配置与逐项说明见 [ESLint说明.md](ESLint说明.md)，此处只记关键步骤与决策。

### 操作步骤

1. `npm i -D eslint typescript-eslint @eslint/js globals`（实际装到 ESLint 10.13、typescript-eslint 8.72）。
2. 新建 `eslint.config.js`（flat config，项目是 ESM 所以直接写 ESM）：

- `ignores`：`dist`、`node_modules`、`test-results`、`playwright-report`、`tests/e2e/__snapshots__`
- `eslint.configs.recommended`：ESLint 核心推荐规则，覆盖全部文件
- TS 文件块（`**/*.ts`）：`tseslint.configs.recommendedTypeChecked` 类型感知规则集，`globals.browser`
- Node 环境文件块（`vite.config.ts`、`playwright.config.ts`、`tests/e2e/**/*.ts`）：覆盖为 `globals.node`

3. `package.json` 新增 `lint` 脚本，并把 `lint` 接进 `ci` 脚本的第一位（在 `format:check` 之前）。
4. `AGENTS.md` 同步更新。

### 设计决策与注意事项

**类型感知检查（`projectService: true`）。** lint 基于 tsconfig 拿类型信息，能发现普通 lint 抓不到的问题（如浮空 Promise、错用 Promise 的 API）。projectService 原生支持解决方案式根配置（`files: []` + references），会按文件归属自动选用 `tsconfig.app/node/e2e` 中的对应项目。

**未被任何 tsconfig 项目覆盖的 TS 文件会被 projectService 直接拒绝。** 这是特性而非缺陷：它强制任何新增 TS 文件必须纳入对应 tsconfig 的 `include`，与缺口二的覆盖完整性互为保险。代价是报错信息（"was not found by the project service"）对不熟悉此机制的人略费解，已写进 `AGENTS.md` 提示。

**按运行环境分块的 globals。** `no-undef` 保持开启，浏览器代码用 `globals.browser`（`document`/`window`），构建配置与 Playwright 用例用 `globals.node`（`process` 等），拼错全局变量名会被直接抓住。

**未引入 `eslint-config-prettier`。** typescript-eslint v8 的推荐集不含格式类规则，与 Prettier 无重叠冲突，少一个依赖。

**自定义规则。** `@typescript-eslint/no-explicit-any` 为 error（禁用显式 any，tsc 的 strict 管不到这一点）；`no-console` 为 warning（允许但不鼓励，不阻断 CI）。

### 验证结果

- `npm run lint`：现有代码零告警通过（含首次被 lint 的 WebGPU 异步代码与 e2e 用例）
- 用临时文件验证规则真实生效：`any` → error、`console.log` → warning、项目外 TS 文件 → 被 projectService 拒绝
- `npm run format:check`、`npm run build`、`npm test` 全部通过
